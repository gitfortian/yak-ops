## 1. Goal

v1.0.0 已经证明 Yak Ops 可以完成可部署、可验收的数据同步核心链路。

v1.1.0 不以横向增加 Connector 数量为主目标，而是解决：

> 已发布的数据同步任务能否稳定地自动运行，并在常见失败或进程重启后以明确规则继续工作。

版本主题：

```text
Automation & Recovery
```

## 2. Core Scope

v1.1.0 最终冻结范围聚焦自动运行、失败恢复和运行诊断：

```text
Offline Scheduling
Execution Retry / Attempt
Offline Concurrency Policy
Realtime Desired State / Auto Recovery
Execution Product Event Log
YakFlow Runtime Trace
Offline Execution Diagnostics
```

Operations Center 同步补齐自动运行与恢复所需的聚合运行态信息；OFFLINE Task Detail 增加 Runtime Trace 驱动的执行诊断。

## 3. Offline Scheduling

Offline Task 在现有手工运行之外增加定时运行能力。

PR1 已建立 [Data Sync Scheduler Contract](../capabilities/data-sync/scheduler.md) 与 Quartz Boundary：

- Business 只依赖框架无关 `ScheduleEngine`。
- Quartz 依赖只进入 Boot。
- JobData 只保存稳定 ID。
- Cron 使用显式 Time Zone。
- misfire 固定为 `DO_NOTHING`。
- PR1 不新增 Schedule 表、不创建 Instance、不实现并发策略和 Retry。

PR2 已完成 Offline Schedule Persistence + Trigger：

- v1.1.0 最终 `V2__v1_1_0.sql` 的 Offline Schedule section 新增 Schedule persistence。
- Schedule 以 Yak Ops DB 为 Source of Truth。
- 支持保存、查询、启用、停用 Schedule。
- 新 Schedule 默认 disabled。
- 启用要求 Task = PUBLISHED + OFFLINE。
- Quartz Fire 创建 `triggerType=SCHEDULE` Instance。
- 已有 Active Instance 时固定 skip。
- Task unpublish 自动 disable Schedule。
- RAMJobStore 场景下应用启动会从 DB 恢复 enabled Trigger。

PR4 / PR6 已完成 Retry / Attempt Runtime 与 Operations Center 运行态观察。本次 `Offline Sync Schedule Configuration UI Closure` 因发现 Schedule Definition 缺少用户配置入口而重新打开 v1.1 Contract：OFFLINE 编辑页补齐 Cron / Time Zone，OFFLINE Task List 承担显式 Enable / Disable；Operations Center 保持运行态观察。v1.1 的并发策略仍只承诺 `SKIP_IF_RUNNING`，不扩展 QUEUE / PARALLEL。

第一阶段至少支持：

- Cron Schedule。
- 显式 Time Zone。
- Schedule Enable / Disable。
- 下次触发时间。
- Trigger Source 区分 MANUAL / SCHEDULE。
- 只有 PUBLISHED Task 可以被调度执行。

Scheduler 只负责产生执行请求，不复制 Data Sync Runtime。

## 4. Retry / Attempt

PR3 已冻结 [Execution Retry / Attempt Contract](../capabilities/data-sync/execution-retry-attempt.md)。

身份模型：

```text
Task
  ↓
Execution = existing DataSyncInstance
  ├── Attempt #1
  ├── Attempt #2
  └── Attempt #3
```

关键规则：

- 现有 `DataSyncInstance` 保持稳定 Execution Root 身份。
- v1.0 / early v1.1 Instance 视为只有一个隐式 Attempt #1。
- Retry 创建新的 Attempt，不创建新的 Execution。
- root trigger 继续保持 MANUAL / SCHEDULE；Retry 不覆盖 root trigger。
- 所有 Attempts 复用同一个 `taskVersion + definitionSnapshot`。
- `maxAttempts` 包含第一次执行。
- v1.1 第一阶段使用固定 `backoffSeconds`。
- Generic Retry 只处理 FAILED。
- CANCELED / LOST 不自动 Retry。
- backoff 期间 Execution 仍属于 Active。
- Attempt 指标不能简单累加成 Execution 业务同步量。

PR3 只定义 Contract，不新增 Attempt Table、自动 Retry、Retry Policy API 或 UI。

PR4 已完成 Retry / Attempt Persistence + Runtime：

- v1.1.0 最终 `V2__v1_1_0.sql` 的 Execution Retry / Attempt section 新增 Retry / Attempt persistence。
- Task 持久化 `maxAttempts / backoffSeconds` Retry Policy。
- 默认 `maxAttempts=1`，升级后旧任务保持原行为。
- Execution Root 新增 `currentAttempt / nextRetryTime` 等冻结运行状态。
- 新增 `yak_ops_data_sync_attempt` Attempt History。
- Execution 新增 `RETRY_WAITING`。
- OFFLINE / REALTIME FAILED Attempt 都可按固定 Backoff 自动 Retry。
- Retry 不创建新 Execution，不改变 root trigger，不读取最新 Task Definition。
- CANCELED / LOST 不自动 Retry。
- Attempt History 提供只读 API。
- RETRY_WAITING 继续视为 Active Execution。
- Retry Backoff 不使用 Quartz，也不跨进程恢复。

## 5. Offline Concurrency Policy

同一个 Offline Task 被重复触发时必须存在明确并发语义。

v1.1.0 第一阶段只承诺：

```text
SKIP_IF_RUNNING
```

不在本版本承诺 QUEUE / PARALLEL。

## 6. Realtime Desired State / Auto Recovery

PR5 已实现 [Realtime Desired State + Auto Recovery](../capabilities/data-sync/realtime-desired-state.md)。

REALTIME Task 增加：

```text
desiredState = STOPPED / RUNNING
```

用于区分：

```text
用户希望停止
vs
进程异常导致停止
```

行为：

```text
Start REALTIME
    ↓
desiredState = RUNNING

Stop / Unpublish
    ↓
desiredState = STOPPED
```

应用启动：

```text
old PENDING / RUNNING / RETRY_WAITING Execution
        ↓
LOST
        ↓
PUBLISHED + REALTIME + desiredState=RUNNING
        ↓
create new AUTO_RECOVERY Execution
        ↓
reuse same task + definitionVersion CDC state
        ↓
continue from completed Debezium offset
```

首次升级时，v1.1.0 Release Migration 的 Realtime Desired State / Auto Recovery section 会把升级前仍存在 active REALTIME Execution 的已发布 Task 回填为 RUNNING，避免升级后静默停止。

该能力继续保持：

```text
at-least-once
```

不因为自动恢复而声明 exactly-once，也不复活旧 Instance。

PR5 不提供常驻 watchdog、多节点 fencing 或 distributed recovery。

## 7. Operations Center

v1.1.0 最终职责边界：

- Operations Center 是 OFFLINE / REALTIME 的跨 Task 聚合可观察性 Dashboard。
- Dashboard 展示 Execution 数量、状态分布、持久化读写指标聚合、耗时聚合、异常 Task / Execution、AUTO_RECOVERY 趋势与失败排行。
- OFFLINE 编辑页负责可选 Cron / Time Zone Schedule Definition；保存 Schedule 不会隐式启用。
- OFFLINE Task List 负责一次手工 Run 快捷入口以及显式 Schedule Enable / Disable。
- Task Detail 负责 Task-scoped 的只读 Execution / Attempt 详情。
- REALTIME 继续区分 desiredState 与实际 Execution 状态，并在运行详情中明确 AUTO_RECOVERY。
- Attempt History 只在真实重试存在或 `RETRY_WAITING` 时展开，不把 Attempt 平铺成新的 Execution。

Data Integration 继续负责 Definition / Publish 以及 Task-scoped 只读运行详情；Operations Center 不复制 Task / Instance 控制面。

## 8. Offline Runtime Diagnostics

最终封板前补齐离线同步执行诊断能力：

- YakFlow API 新增 JDK-only `RuntimeTraceEvent / RuntimeTraceListener` 旁路契约。
- JDBC Source 记录 Split planned / started / finished / failed，以及生成 SQL、Split 范围、读取行数和完整读取耗时。
- JDBC Sink 记录 Writer SQL Template、Batch Size、Batch rows、`executeBatch` / commit 耗时与失败阶段。
- Trace 禁止记录 YakRow 业务字段值和 Sink bind 参数。
- Offline Attempt 使用 file-backed Trace Store 保存 JSONL 分片与 Summary，文件根位于 `${yak.ops.home}/data/data-sync/execution-traces`。
- Trace Store / Listener 故障不得反向改变 Data Sync Runtime 结果。
- OFFLINE Task Detail 的第三个 Tab 为 `执行诊断`，按 Summary → Error → Source Split → Target Batch → Lifecycle Events 展示。
- 生命周期产品事件继续保留，但作为辅助审计信息，不再承担 OFFLINE 诊断主视图。
- REALTIME 继续使用产品事件日志，本版本不提供 REALTIME Runtime Trace。

Runtime Trace rows / durations 是诊断事实，不替代 Execution / Attempt 持久化 readRows / writeRows 指标，也不据此声明 exactly-once 或构造浏览器端 TPS。

## 9. Database Migration

v1.0.0 已发布，因此：

```text
V1__baseline.sql = immutable
```

v1.1.0 正式发布前的开发过程曾按能力拆成 V2 ~ V5 Draft Migration。由于这些 Draft 尚未发布、且只进入可重建开发 / E2E 环境，Release Freeze 阶段已按原执行顺序收口为一个正式 Release Migration：

```text
v1.0.0
└── V1__baseline.sql

v1.1.0
└── V2__v1_1_0.sql
```

`V2__v1_1_0.sql` 按原 Draft 顺序包含：

```text
Offline Schedule
→ Execution Retry / Attempt
→ Realtime Desired State / Auto Recovery
→ Execution Product Event
```

Squash 只整理未发布的开发历史，不重写已验证 SQL 语义。当前 `V1__baseline.sql` 与 `v1.0.0` Tag 保持一致。

v1.1.0 正式发布后，`V2__v1_1_0.sql` 与 V1 一样永久冻结；后续版本只能通过更高 Flyway Version 的 Release Migration forward-fix。

Execution Product Event section 只从 v1.1.0 Migration 生效后记录新事件，不为历史 Execution 伪造事件时间线。

## 10. Compatibility

v1.1.0 必须保持：

- Product Version 与 Task `definitionVersion` 相互独立。
- 已有 v1.0.0 Task Definition 可以继续读取。
- 已有 Realtime persisted offset / schema history 不因产品版本升级自动失效。
- Workspace ownership 与 Datasource secret boundary 不变。
- 现有手工运行能力继续可用。

## 11. Explicit Non-Goals

以下能力不属于 v1.1.0：

- Auto Create Table。
- Logical Data Modeling。
- Multi-table Task。
- Transform。
- PostgreSQL CDC。
- Paimon / Hive / File Connector expansion。
- Distributed Runtime。
- Multi-node Worker。
- HA / Leader Election。
- Exactly-once transaction coordination。
- DAG Workflow。
- QUEUE / PARALLEL Offline concurrency。
- Enterprise RBAC。

## 12. Required Acceptance

PR7 新增独立的 `Data Sync Automation Acceptance` CI Job，并建立 [v1.1 Automation & Recovery 验收矩阵](../e2e/data-sync/automation/README.md)。

v1.1.0 除继续执行现有 Quality Gate、JDBC Acceptance、MySQL CDC Cross-Database Acceptance 外，还必须覆盖：

- Cron 到点触发一次 Offline Execution。
- Disable Schedule 后不再触发。
- RUNNING Task 命中 SKIP_IF_RUNNING 后不创建并发执行。
- Retry Policy 按最大 Attempt / Backoff 生效。
- Stop / Cancel 不被误判成可自动 Retry。
- Realtime desiredState=RUNNING 在应用重启后创建新 Instance。
- Realtime 自动恢复继续复用同 definitionVersion 的 persisted CDC state。
- Realtime 自动恢复不会静默退化为 fresh snapshot。

自动化证据：

```text
QuartzScheduleEngineTest
        +
DataSyncAutomationAcceptanceIT
        +
OfflineSyncJdbcAcceptanceIT
        +
MySqlCdcIntegrationIT
```

手工必选：

```text
AUTOMATION-001 离线 Cron 调度与停用
AUTOMATION-002 实时同步进程重启自动恢复
```

PR7 只定义并接入验收门禁与手工流程；正式 Release 前的人工执行结果由后续 Release Readiness / Evidence 记录。
