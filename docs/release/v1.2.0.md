## 1. Release Goal

v1.2.0 在 v1.1.0 的调度、Retry / Attempt、Realtime Desired State、Auto Recovery 与运行诊断基础上，重点解决两件事：

```text
数据库结构由系统理解
        +
运行策略由系统规划
```

对应产品目标：

```text
Schema-Aware
→ 读取 Source Metadata
→ 归一 Logical Type
→ 建立 Column Mapping
→ 规划 Target Schema / DDL
→ 运行前重新校验真实数据库结构

Smart Runtime
→ 普通用户不填写底层运行参数
→ OFFLINE AUTO Runtime Planning
→ Execution 冻结 Effective Config
→ SMART Retry 判断是否值得重试
→ RETRY_WAITING 跨进程继续同一 Retry Chain
```

本版本不把更多可配置项暴露给普通用户；相反，v1.2.0 的产品方向是减少引擎参数、保留可观察事实，并把可推导的运行决策内化到系统。


## 2. Frozen Core Scope

### 2.1 Schema-Aware Sync

v1.2.0 冻结包含：

- Schema / Logical Table 产品 Contract。
- Source Metadata Introspection。
- Logical Type Normalization，复用 YakFlow `YakDataType`，不建立第二套类型枚举。
- Composite Primary Key 顺序保留。
- Target Table Planner。
- MySQL / PostgreSQL / Oracle Target Native Type Mapping。
- CREATE TABLE DDL Planning。
- Table / Column Comment DDL Planning 与自动建表元数据保留。
- Runtime Target Schema Compatibility Re-check。
- 显式 `autoCreateTable`。
- Auto Create / Schema Preview API 与 Task Editor UI。
- 完整 DDL 通过目标表辅助入口按需查看，不在普通表单持续铺开说明。

主链：

```text
Datasource Catalog
        ↓
LogicalTable
        ↓
YakTableSchema
        ↓
Target Table Plan
        ↓
Schema Compatibility
        ↓
Controlled Auto Create
        ↓
Runtime Re-check
```

### 2.2 Column Mapping

v1.2.0 冻结包含：

- Task 级 Column Mapping Contract 与 Persistence。
- `mapping = null` 保持历史大小写不敏感同名映射兼容。
- 显式字段子集、字段重排、字段改名。
- Schema Mapping Editor：同名 / 同序 / 手工连接、删除、清空中间态与字段搜索。
- Auto Create 目标不存在时允许定义目标字段名。
- Mapping-Aware Source Read Schema / Target Logical Schema。
- Mapping 进入 Task `definitionVersion` 比较并冻结到 Execution Snapshot。
- OFFLINE MySQL Source → MySQL / PostgreSQL / Oracle JDBC Cross-Database Acceptance。
- REALTIME MySQL CDC → MySQL / PostgreSQL / Oracle 主键 Mapping、Snapshot、INSERT / UPDATE / DELETE Acceptance。

Mapping 不提供表达式、自定义 SQL、CAST 或 Transform。

### 2.3 Smart Runtime

v1.2.0 冻结包含：

- Runtime Policy 内化：普通 Task Editor 不暴露 fetch / batch / split / parallelism / checkpoint / queue / timeout 等引擎调优参数。
- OFFLINE Runtime Policy 稳定语义为 `AUTO / FIXED`。
- 新建普通 OFFLINE Task 省略 Runtime Config 时，由后端物化 AUTO Policy。
- 历史无 policy 或显式 API Runtime Config 未声明 policy 时按 FIXED 兼容。
- `OfflineRuntimePlanner` 使用 Mapping 后 Source Logical Schema、受控 Source Statistics 与 Target 类型规划 Effective Runtime Config。
- Statistics 失败属于优化降级，回退整表单并行，不额外阻断原本可运行的同步。
- Effective Runtime Config 与 Planning Summary 只在根 Execution 创建时计算一次并冻结到 `definitionSnapshot`。
- 同一 Execution 的 Retry Attempt 复用冻结配置，不重新规划。

当前 AUTO Planning 只对满足安全条件的 Source 使用 MIN / MAX / COUNT 与整数主键 split；不把通用数据库统计、成本模型或自适应在线调参纳入 v1.2.0。

### 2.4 Smart Retry + Durable Recovery

v1.2.0 冻结包含：

- Retry Policy 稳定模式为 `SMART / FIXED`。
- 新建普通 Task 省略 Retry Policy 时，由后端物化 SMART：最多 3 次 Attempt，15 秒起始退避。
- 历史 / 显式无 mode Policy 按 FIXED 兼容。
- Task Editor 不提供 Retry Policy 配置 UI；查询与 Execution Snapshot 仍展示冻结后的策略事实。
- SMART 只对明确瞬时失败自动 Retry；SQL / Schema / 权限 / 完整性约束 / 产品校验 / 非法参数 / 能力不支持 / 未知异常不自动重试。
- 写入安全优先于错误分类：OFFLINE APPEND / OVERWRITE Runtime 已启动后不自动重放；UPSERT / REALTIME CHANGELOG 可对明确瞬时失败继续 SMART Retry，但不承诺 exactly-once。
- SMART Backoff 使用确定性倍增并限制上限。
- `nextRetryTime` 持久化。
- `RETRY_WAITING` 期间进程退出后，启动恢复继续同一个 Execution Root / taskVersion / definitionSnapshot / Attempt Chain。
- Durable Retry Recovery 先于 REALTIME desired-state reconciliation，避免重复创建 AUTO_RECOVERY Root。

### 2.5 Task Lifecycle Product Closure

v1.2.0 同时冻结已经落地主路径的列表级运行入口：

```text
OFFLINE
运行
+
Schedule 启动 / 停止

REALTIME
启动 / 停止 / 重新启动
```

REALTIME 使用已有 Run / Cancel Contract：

- 已上线 + STOPPED + 无活动 Execution → `启动`。
- PENDING / RUNNING / RETRY_WAITING → `停止`。
- `desiredState=RUNNING` 但当前无活动 Execution → `重新启动`。
- 未上线 Task 的启动入口禁用。

Task Detail 继续只读，Operations Center 继续以跨 Task 聚合观察为主，不因为列表快捷入口建立第二套 Runtime 模型。

## 3. Version Boundary

Product Version 与 Data Sync Task `definitionVersion` 继续保持独立：

```text
Product Version
1.2.0-SNAPSHOT
→ Yak Ops 产品开发线

Task definitionVersion
v1 / v2 / v3 / ...
→ 单个 Data Sync Task 的可执行定义
```

升级 Product Version 不得自动修改 Task `definitionVersion`，也不得仅因产品版本变化创建新的 REALTIME CDC state identity。

Task executable definition 当前包括 Mapping、Runtime / Retry Policy 等稳定执行语义；普通 UI 隐藏引擎参数不等于删除这些 Contract，也不能在编辑时用当前系统默认值覆盖历史 Task 已持久化配置。

## 4. Database Boundary

v1.2.0 开发开始时，已发布且永久冻结的 Flyway 历史为：


Release Freeze 前，v1.2 Schema 变化曾拆成两个未发布 Draft：


这两个 Draft 只属于可重建开发 / E2E 历史。当前 Release Freeze 已按原 SQL 顺序和语义 squash 为唯一 v1.2 Release Migration：

```text
V3__v1_2_0.sql
```

V3 依次包含：

```text

→ Data Sync Column Mapping
```

具体变化：

- 为 Task 增加 `auto_create_table`，默认关闭，旧 Task 保持“目标表必须存在”的行为。
- 为 Task 增加可空 `mapping_config`；NULL 保持旧 Task 隐式同名 Mapping。

Post-squash Review 结论：**PASS**。

- V1 / V2 未修改。
- 原 V3 / V4 Draft 已删除。
- Squash 保留原 Draft 的执行顺序、字段定义、默认值、Comment 与 AFTER 位置。
- 没有借 Release Freeze 增加数据回填、重写字段类型或重新设计 Schema。
- 当前 Flyway Version 连续为 V1 → V2 → V3。
- 当前 Product Version 只有一个 Release Migration。
- `scripts/release/check-release-migration.sh 1.2.0` 必须在正式 Release Gate 再次通过。

`V3__v1_2_0.sql` 当前是**已冻结但尚未发布**的 v1.2 Release Migration。后续如果发现 P0 / P1 Release Blocker 必须修改其内容，需要显式重新打开 Migration Freeze、记录原因并重新完成 Migration Review；不能静默修改 checksum。正式发布 v1.2.0 后，V3 与 V1 / V2 一样永久不可变。

```text
Contract / Unit

├── Schema Compatibility / Preflight
├── Mapping Contract / Schema Resolution
├── Offline Runtime Planner
├── SMART Retry Classification / Lifecycle

Real Database Acceptance
├── OfflineSyncJdbcAcceptanceIT
│   └── MySQL Source → MySQL / PostgreSQL / Oracle
│       + Auto Create / Mapping / DDL

    └── MySQL CDC → MySQL / PostgreSQL / Oracle
```

## 6. Required Manual E2E

Scope Freeze 已冻结 v1.2.0 的最小新增人工验收目标；三个可重复 Procedure 已准备完成，但尚未记录真实人工 PASS Evidence。

```text
MAPPING-001
OFFLINE MySQL → PostgreSQL
Auto Create + Column Mapping + DDL / Comment + AUTO Runtime

MAPPING-002
REALTIME MySQL CDC → PostgreSQL
Auto Create + PK Rename + Snapshot + INSERT / UPDATE / DELETE
+ Start / Stop / Restart

RECOVERY-001
Durable Retry Recovery
RETRY_WAITING 期间重启 Yak Ops
→ 保留同一 Execution Root
→ 按 nextRetryTime 继续下一 Attempt
```

人工 E2E 验证用户可见产品链路，不扩展为数据库 × 写入模式 × 参数的笛卡尔积。SMART Retry 的异常分类矩阵以自动测试为主要证据。

[Column Mapping Manual E2E](../e2e/data-sync/mapping/README.md) 提供 MAPPING-001 / MAPPING-002；[RECOVERY-001](../e2e/data-sync/recovery/01-durable-retry-recovery.md) 提供 Durable Retry Recovery。三个场景都已进入 v1.2 Required Manual E2E，但“Procedure Ready”不等于“已执行”。执行结果统一进入 [v1.2.0 Release Readiness](./v1.2.0-readiness.md)。

## 7. Frozen Non-Goals

以下能力明确不进入 v1.2.0；后续实现默认进入 v1.3+ 或新的版本 Contract：

- Logical Table Persistence。
- Catalog Refresh / Schema Diff。
- DDL Sync / Automatic Schema Evolution。
- Multi-table Task。
- Transform / Expression / Custom SQL Mapping。
- PostgreSQL CDC 或更多 CDC Source。
- 用户可配置的 Runtime Tuning UI。
- 用户可配置的 Retry Policy UI。
- Continuous Realtime Reconciliation / 常驻 Watchdog。
- Runtime Trace Retention、对象存储、全文检索或 REALTIME Runtime Trace。
- 通用 YakFlow Checkpoint 跨进程恢复。
- Distributed Runtime / Worker / HA / leader election / fencing。
- Exactly-once transaction coordination。

尤其是 REALTIME：

```text
v1.2
Startup Reconciliation = IN
Durable Retry Recovery = IN
Manual Restart = IN

Continuous Watchdog = OUT
```

`desiredState=RUNNING` 且没有活动 Execution 的差异由产品显示为“重新启动”；v1.2.0 不引入后台常驻协调器自动无限拉起。
