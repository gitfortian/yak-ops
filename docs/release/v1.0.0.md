# Yak Ops v1.0.0 Release Contract

Status: Candidate

Target Version: `1.0.0`

Target Tag: `v1.0.0`

Distribution: `yak-ops-1.0.0.tar.gz`

Docker Images:

```text
weifuwan/yak-ops:1.0.0
weifuwan/yak-ops-api:1.0.0
```

Depends On:

- [Yak Ops Version Management](./README.md)
- [Yak Ops Architecture](../../ARCHITECTURE.md)
- [Data Sync Capability](../capabilities/data-sync/README.md)
- [Data Sync Manual E2E](../e2e/data-sync/README.md)

## 1. Goal

`v1.0.0` 是 Yak Ops 第一个稳定产品版本。

V1 的目标不是覆盖完整数据平台能力，而是做到：

> 当前核心能力边界清晰、主链路可完整使用、可以重复部署、可以明确验收、发布物可以追溯到唯一代码版本。

V1.0.0 只有在本文件 Release Checklist 全部满足后，才允许创建正式 Tag。

## 2. Product Surface

V1 产品面由三部分组成：

```text
Data Integration
├── Datasource
├── Offline Sync Definition
└── Realtime Sync Definition

Operations Center
├── Offline Task Operations
└── Realtime Task Operations

Management Center
├── User Management
└── Workspace Management
```

Platform 的 Security / Workspace / User Preference 是产品支撑能力，不作为第二套产品域。

## 3. Platform Scope

V1 必须支持：

- 用户登录、退出和当前身份。
- 用户管理。
- Workspace 生命周期与成员关系。
- Workspace 请求隔离。
- 当前用户 Workspace 选择保持。
- 用户偏好持久化。
- 产品收藏 / 常用入口所需的用户级偏好能力。

关键验收：

- 未登录用户不能访问需要认证的产品页面。
- 用户不能通过修改 Workspace Header 访问自己不属于的 Workspace 数据。
- 同一个用户重新登录后可以恢复仍然有效的 Workspace 选择。
- 不同用户不能继承彼此的 Workspace 选择。
- User Preference 保持 user-scoped，不变成 Workspace-scoped 数据。

## 4. Datasource Scope

V1 内置数据库范围：

```text
MySQL 5 / 8
PostgreSQL
Oracle
```

V1 Datasource 必须支持：

- Workspace-scoped Datasource CRUD。
- 新增 / 编辑表单。
- Structured JDBC Connection。
- JDBC URL Preview。
- Advanced Properties。
- Saved Connection Test。
- Batch Delete。
- Batch Connection Test。
- Catalog Metadata 读取。
- 数据库 / Schema Scope 规则。
- MySQL 5 / 8 Driver 隔离。

关键验收：

- Connection Test 必须建立真实物理连接，不能伪通过。
- Datasource Credential 不得进入普通 Task Snapshot、日志或前端无必要响应。
- Datasource 资源 ID 不能绕过 Workspace Scope。
- 前端可以选择的 V1 内置数据库类型必须存在可工作的后端 Provider。

## 5. Data Sync Task Definition Scope

V1 支持：

```text
OFFLINE
REALTIME
```

Task Definition 必须支持：

- Workspace ownership。
- Source / Target Datasource。
- Source / Target Table。
- Catalog 驱动的字段映射与兼容性验证。
- `UNPUBLISHED / PUBLISHED` 发布状态。
- Publish / Unpublish。
- Save / Save & Publish。
- executable definition 变化时推进 `definitionVersion`。
- metadata-only 变化不创建新的 `definitionVersion`。
- 发布中的 Task 不直接修改 executable definition。
- 只有已发布 Task 可以创建新的运行 Instance。

Product Version 与 Task `definitionVersion` 必须保持完全独立。

## 6. Offline Sync Scope

V1 Source：

```text
MySQL
```

V1 Target：

```text
MySQL
PostgreSQL
Oracle
```

V1 Write Mode：

```text
APPEND
OVERWRITE
UPSERT
```

V1 Offline 必须支持：

- 手工启动。
- Task Instance 持久化。
- `PENDING / RUNNING / SUCCEEDED / FAILED / CANCELED / LOST` 现有生命周期语义。
- Stop / Cancel。
- `readRows / writeRows` 指标。
- APPEND。
- OVERWRITE。
- Native UPSERT。
- JDBC Source split。
- Source parallelism。
- MySQL → MySQL/PostgreSQL/Oracle 自动化 Acceptance。

Operations Center 负责：

- 手工执行。
- Stop。
- Instance 列表。
- Instance Detail。
- 运行状态展示。

Data Integration 中的 Offline Sync 负责：

- Task Definition。
- 编辑。
- Publish / Unpublish。
- Definition 与 Instance 的跨页面导航。

## 7. Realtime Sync Scope

V1 Source：

```text
MySQL CDC
```

V1 Target：

```text
MySQL
PostgreSQL
Oracle
```

V1 Realtime 必须支持：

- Debezium initial snapshot。
- Binlog continuous streaming。
- INSERT。
- UPDATE。
- DELETE。
- JDBC CHANGELOG apply。
- 手工 Start。
- Stop。
- persisted Task Instance。
- active Instance runtime presentation。
- `readRows / writeRows` change-event metrics。
- checkpoint。
- file-backed Debezium offset。
- schema history。
- same Task + same `definitionVersion` 状态复用。
- 新 Instance 从已完成 offset 继续。
- MySQL CDC → MySQL/PostgreSQL/Oracle 自动化 Acceptance。

V1 恢复语义明确为：

```text
at-least-once
```

V1 不声称 exactly-once。

应用进程重启后：

```text
old PENDING / RUNNING Instance
        ↓
       LOST

same Task + same definitionVersion
        ↓
new Instance
        ↓
reuse persisted CDC state
        ↓
continue from completed offset
```

这属于 connector-state continuation，不属于旧 Instance resurrection。

## 8. Operations Center Scope

V1 Operations Center 提供独立产品 Shell。

菜单：

```text
任务运维
├── 离线任务
└── 实时任务
```

职责边界：

- Data Integration 负责定义和发布。
- Operations Center 负责运行和运行态观察。
- Operations Center 不编辑 Task Definition。
- Operations Center 不执行 Publish / Unpublish。
- Task execution 与 Instance history 作为独立 Tab。
- Instance 可以按 Task 过滤。
- 离线 / 实时复用共享 Instance Runtime 能力，不复制两套生命周期实现。

## 9. Management Center Scope

V1 Management Center 至少提供：

- User Management。
- Workspace Management。
- Workspace Member Management。

V1 不要求通用 RBAC 平台。

## 10. Packaging Scope

V1 必须产生：

```text
yak-ops-1.0.0.tar.gz
```

Distribution 至少包含：

- Backend executable JAR。
- Frontend built assets。
- Runtime config。
- Run script。
- 内置 MySQL Driver。
- LICENSE。
- NOTICE。
- README。

V1 Docker 必须产生：

```text
weifuwan/yak-ops:1.0.0
weifuwan/yak-ops-api:1.0.0
```

镜像必须来源于同一个 V1 Distribution。

## 11. Deployment Scope

V1 至少支持两种 Compose 方式：

- 内置 MySQL 的 `compose.yaml`。
- 使用外部 MySQL 的 `compose.without-mysql.yaml`。

正式发布必须通过最小部署 Smoke Test：

```text
Database Ready
   ↓
Backend Ready
   ↓
Frontend Ready
   ↓
Login Page
   ↓
Login
   ↓
Open Product
```

生产部署必须显式配置 Datasource Master Key。

生产环境不能把示例默认密码当作安全默认值。

## 12. Required Automated Verification

V1 Release 前必须通过：

### Quality Check

- Backend logging rules。
- Backend format。
- Backend compile。
- Backend verify。
- Frontend format。
- Frontend lint。
- Frontend type check。
- Frontend architecture。
- Frontend build。

### Full Backend Acceptance

Release 时不使用 path filter 跳过：

- JDBC Acceptance。
- MySQL CDC Cross-Database Acceptance。

自动 Acceptance 必须继续覆盖：

```text
Offline
MySQL → MySQL
MySQL → PostgreSQL
MySQL → Oracle

Realtime
MySQL CDC → MySQL
MySQL CDC → PostgreSQL
MySQL CDC → Oracle
```

Realtime Acceptance 还必须证明：

- initial snapshot。
- INSERT / UPDATE / DELETE。
- checkpoint completion。
- persisted offset。
- cancel。
- state-directory reuse。
- restart continuation。
- 第二次运行不会静默退化成 fresh snapshot。

## 13. Required Manual E2E

Manual E2E 验证产品 UI 主链路，不复制自动化 Cross-Database Matrix。

V1 正式 Release 必须通过以下 5 个场景：

- `OFFLINE-001`：MySQL → MySQL / APPEND。
- `OFFLINE-002`：MySQL → MySQL / OVERWRITE。
- `OFFLINE-003`：MySQL → MySQL / UPSERT。
- `REALTIME-001`：MySQL CDC → MySQL / initial snapshot + INSERT / UPDATE / DELETE。
- `REALTIME-002`：MySQL CDC Stop → new Instance → Continue Offset。

完整操作入口：

- [Data Sync Manual E2E](../e2e/data-sync/README.md)
- [v1.0.0 Release Readiness](./v1.0.0-readiness.md)

`REALTIME-002` 必须在停止前等待 checkpoint 稳定，并证明第二个 Instance 只消费停止期间新增的 1 个事件；否则不能把“最终数据看起来正确”当作续传能力已经通过。

Cross-Database MySQL/PostgreSQL/Oracle 的完整矩阵继续由自动化 Acceptance 负责；只有当产品 UI 存在数据库特有行为时才增加对应 Manual E2E。

## 14. Explicit Non-Goals

以下能力明确不属于 V1.0.0 Release Blocker：

- Scheduler / Cron。
- 自动重试策略。
- Distributed Runtime。
- Multi-node Worker。
- HA / Leader Election。
- Exactly-once transaction coordination。
- 旧 `LOST` Instance 自动复活。
- 通用 Runtime checkpoint restoration。
- Auto Create Table。
- DDL propagation。
- Schema Evolution。
- Transform。
- Multi-table Task。
- 通用 RBAC / Enterprise Permission Matrix。
- Persisted checkpoint history UI。
- 复杂资源调度。

这些能力只有进入后续版本 Contract 后，才成为对应版本的验收范围。

## 15. Database Freeze

`v1.0.0` 正式 Tag 创建后：

- `V1__baseline.sql` 立即成为不可修改历史。
- 所有新数据库变化必须创建新的 Flyway Migration。
- 不允许为了兼容新代码回改 V1 baseline。

因此，V1 正式发布前必须确认当前 baseline 已经包含 V1 所有必要表结构和约束。

## 16. Release Evidence

`.github/workflows/v1-release-gate.yml` 会为通过自动门禁的候选 Commit 生成 Release Candidate Evidence，包含 Distribution SHA-256、候选 Commit、Docker Image Tag 和本地 content-addressed Image ID。

Registry manifest digest 只有在不可变版本镜像真正推送后才能产生，因此最终正式 Release Evidence 需要在 Publish 步骤补充 Registry Digest，不能把候选 Image ID 冒充远端 Registry Digest。

V1 正式发布时必须记录：

- `v1.0.0` Tag。
- Release Commit SHA。
- Quality Check 结果。
- Full Backend Acceptance 结果。
- Manual E2E 验收记录。
- `yak-ops-1.0.0.tar.gz`。
- Distribution SHA-256。
- `weifuwan/yak-ops:1.0.0` Digest。
- `weifuwan/yak-ops-api:1.0.0` Digest。
- Release Notes。
- Known Limitations。

## 18. Release Decision

只有当第 17 节全部必选项通过时：

```text
v1.0.0 MAY BE RELEASED
```

才允许：

```bash
git tag v1.0.0
```

如果任一 Release Blocker 存在：

```text
DO NOT TAG
DO NOT PUBLISH LATEST
```

修复后重新执行对应 Gate，不通过口头豁免跳过验收。
