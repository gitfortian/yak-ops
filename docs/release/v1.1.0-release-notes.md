# Yak Ops v1.1.0 Release Notes

## Automation & Recovery

Yak Ops v1.1.0 focuses on one question:

> Can a published data-sync task keep operating with clear scheduling, retry and restart semantics instead of depending only on manual execution?

This release adds scheduling, retry attempts, realtime desired state / auto recovery, and Operations Center visibility while keeping the existing Data Sync / YakFlow responsibility boundary.

## Highlights

### Offline Scheduling

Published Offline Tasks can be scheduled with:

- Quartz Cron expressions.
- Explicit time zone.
- Enable / disable.
- Scheduler-computed next fire time.
- `SCHEDULE` Execution trigger source.
- `SKIP_IF_RUNNING` when the same Task already has an active Execution.

Yak Ops DB remains the Schedule source of truth. Quartz is runtime trigger infrastructure and is rebuilt from enabled Schedule definitions after application restart.

### Retry / Attempt

A Data Sync Instance is now the stable Execution root.

One Execution can contain multiple Attempts:

```text
Execution
  ├── Attempt #1 FAILED
  ├── Attempt #2 FAILED
  └── Attempt #3 SUCCEEDED
```

Retry behavior includes:

- `maxAttempts`, including Attempt #1.
- Fixed `backoffSeconds`.
- `RETRY_WAITING` Execution state.
- Independent Attempt metrics / timestamps / error history.
- Stop / Cancel prevents automatic Retry.
- Retry reuses the Execution's immutable taskVersion and definition snapshot.

Retry does not create a new root Execution and does not use Quartz as a Retry timer.

### Realtime Desired State + Auto Recovery

Realtime Tasks now separate user intent from current process state:

```text
Publication State
Desired State
Execution State
```

A user Start sets:

```text
desiredState = RUNNING
```

A user Stop or Unpublish sets:

```text
desiredState = STOPPED
```

After application restart:

- old process-local active Executions become `LOST`,
- a published Realtime Task whose desired state remains RUNNING gets a new `AUTO_RECOVERY` Execution,
- the new Execution keeps the same taskId + definitionVersion CDC state identity,
- Debezium persisted offset / schema history is reused.

Realtime continuation remains at-least-once; this release does not claim exactly-once.

### Operations Center

Operations Center now exposes automation runtime state instead of only idle/running:

- Trigger source.
- Last Run.
- Next Run.
- Schedule Cron / Time Zone.
- Desired State vs actual Realtime Execution state.
- Current Attempt / max Attempts.
- Retry Waiting / next Retry time.
- Latest runtime error.
- AUTO_RECOVERY marker.
- Attempt History in Execution detail.

Data Integration still owns Task Definition and Publish / Unpublish. Operations Center owns running and observing executions.

### Release Acceptance

Backend Acceptance now has three independent layers:

```text
JDBC Acceptance
MySQL CDC Cross-Database Acceptance
Data Sync Automation Acceptance
```

The new Automation Acceptance covers Scheduler, `SKIP_IF_RUNNING`, Retry/Backoff, Cancel no-retry and Auto Recovery identity semantics.

Two v1.1 Manual E2E scenarios are required before formal publication:

- AUTOMATION-001 — Offline Cron scheduling + disable.
- AUTOMATION-002 — Realtime process restart + Auto Recovery.

## Database Upgrade

v1.1.0 adds forward-only migrations:

```text
V2__data_sync_schedule.sql
V3__data_sync_execution_attempt.sql
V4__realtime_desired_state.sql
```

`V1__baseline.sql` remains immutable from v1.0.0.

Upgrade behavior includes:

- existing Tasks default to no automatic Retry unless explicitly configured,
- active published Realtime Tasks are backfilled to desiredState=RUNNING during the V4 upgrade path,
- historical Execution identity remains stable.

## Compatibility

v1.1.0 preserves:

- existing v1.0 Task identity.
- Task `definitionVersion` independence from product version.
- existing Workspace / Datasource ownership boundaries.
- existing persisted Realtime CDC state identity by Workspace / Task / definitionVersion.
- manual Offline / Realtime execution.

## Known Limitations

v1.1.0 deliberately does not include:

- Distributed Runtime / Worker / HA.
- Leader election or distributed fencing.
- Exactly-once transaction coordination.
- QUEUE / PARALLEL Offline concurrency.
- Continuous Realtime recovery watchdog.
- Durable cross-process Retry timer.
- Auto Create Table.
- Logical Data Modeling.
- Multi-table Task.
- Transform.
- PostgreSQL CDC.
- Paimon / Hive / File connector expansion.

Additional UI boundaries:

- Schedule Definition does not yet have a dedicated configuration UI.
- Retry Policy does not yet have a dedicated configuration UI.

The corresponding backend contracts exist and Operations Center can observe their runtime state.

## Deployment Note

Realtime restart continuation depends on the persisted Yak Ops data directory.

Production deployments must preserve:

```text
${yak.ops.home}/data
```

Container replacement must keep the mounted data volume. Deleting that state removes the persisted Debezium offset/schema history required for continuation.
