# Yak Ops v1.1.0 Release Notes

## Automation & Recovery

Yak Ops v1.1.0 focuses on one question:

> Can a published data-sync task keep operating with clear scheduling, retry and restart semantics instead of depending only on manual execution?

This release adds scheduling, retry attempts, realtime desired state / auto recovery, and Operations Center visibility while keeping the existing Data Sync / YakFlow responsibility boundary.

## Highlights

### Offline Scheduling

Published Offline Tasks can be scheduled with:

- Quartz Cron expressions.
- Explicit time zone.
- Enable / disable.
- Scheduler-computed next fire time.
- `SCHEDULE` Execution trigger source.
- `SKIP_IF_RUNNING` when the same Task already has an active Execution.
- Dedicated Offline Task configuration UI for Cron + IANA Time Zone.
- Explicit Schedule enable / disable actions in the Offline Task list after the Task is published; Operations Center remains observability-focused.

Yak Ops DB remains the Schedule source of truth. Quartz is runtime trigger infrastructure and is rebuilt from enabled Schedule definitions after application restart.

### Retry / Attempt

A Data Sync Instance is now the stable Execution root.

One Execution can contain multiple Attempts:

```text
Execution
  ├── Attempt #1 FAILED
  ├── Attempt #2 FAILED
  └── Attempt #3 SUCCEEDED
```

Retry behavior includes:

- `maxAttempts`, including Attempt #1.
- Fixed `backoffSeconds`.
- `RETRY_WAITING` Execution state.
- Independent Attempt metrics / timestamps / error history.
- Stop / Cancel prevents automatic Retry.
- Retry reuses the Execution's immutable taskVersion and definition snapshot.

Retry does not create a new root Execution and does not use Quartz as a Retry timer.

### Realtime Desired State + Auto Recovery

Realtime Tasks now separate user intent from current process state:

```text
Publication State
Desired State
Execution State
```

A user Start sets:

```text
desiredState = RUNNING
```

A user Stop or Unpublish sets:

```text
desiredState = STOPPED
```

After application restart:

- old process-local active Executions become `LOST`,
- a published Realtime Task whose desired state remains RUNNING gets a new `AUTO_RECOVERY` Execution,
- the new Execution keeps the same taskId + definitionVersion CDC state identity,
- Debezium persisted offset / schema history is reused.

Realtime continuation remains at-least-once; this release does not claim exactly-once.

### Operations Center

Operations Center is the cross-Task observability surface for automation and recovery:

- OFFLINE / REALTIME aggregate Dashboard.
- Execution count and status distribution.
- Read / write totals and duration aggregates where persisted metrics support them.
- Realtime abnormal Task / Execution visibility.
- AUTO_RECOVERY trend / marker.
- Failure ranking and recent automation health.

Per-Task definition and runtime controls do not live in the Dashboard. Data Integration owns Task Definition / Publish; the OFFLINE Task List owns manual Run and explicit Schedule enable / disable; Task Detail owns Task-scoped read-only Execution / Attempt inspection.

### Offline Execution Diagnostics

v1.1.0 also adds structured runtime diagnostics for bounded Offline JDBC sync:

```text
Source Split
  → generated SELECT SQL
  → numeric Split range
  → rows read
  → end-to-end read duration

Target Batch
  → SQL Template
  → Batch rows
  → executeBatch duration
  → commit duration
```

The implementation is deliberately separated into three layers:

- YakFlow Runtime Trace Contract + JDBC diagnostic events.
- File-backed Execution Trace Store + read-only diagnostics API.
- OFFLINE Task Detail `执行诊断` UI.

Trace files are stored under:

```text
${yak.ops.home}/data/data-sync/execution-traces
```

Important boundaries:

- Trace is best-effort and never changes Data Sync Runtime success/failure.
- Business row values and Sink bind parameters are not persisted in Trace.
- Trace error messages are sanitized before persistence.
- Large Source / Sink detail uses cursor pagination instead of loading the entire Trace file.
- Lifecycle product events remain available as auxiliary audit context.
- REALTIME Runtime Trace is not included in this release.

### Release Acceptance

Backend Acceptance now has three independent layers:

```text
JDBC Acceptance
MySQL CDC Cross-Database Acceptance
Data Sync Automation Acceptance
```

The new Automation Acceptance covers Scheduler, `SKIP_IF_RUNNING`, Retry/Backoff, Cancel no-retry and Auto Recovery identity semantics.

Two required v1.1 Manual E2E scenarios have been executed and recorded as PASS on 2026-10-04:

- AUTOMATION-001 — Offline Cron scheduling + disable — PASS.
- AUTOMATION-002 — Realtime process restart + Auto Recovery — PASS.

Formal publication still requires the exact `1.1.0` release commit to pass the Release Gate Full Sweep.

## Database Upgrade

v1.1.0 has one forward-only Release Migration:

```text
V2__v1_1_0.sql
```

`V1__baseline.sql` remains immutable from v1.0.0.

V2 groups the v1.1.0 schema changes in release order:

```text
Offline Schedule
→ Retry / Attempt
→ Realtime Desired State / Auto Recovery
→ Execution Product Event
```

The feature-level V2 ~ V5 files used during development were unpublished Draft Migrations and were squashed before release. They are not part of the public Flyway history.

Upgrade behavior includes:

- existing Tasks default to no automatic Retry unless explicitly configured,
- active published Realtime Tasks are backfilled to desiredState=RUNNING during the v1.1.0 upgrade,
- historical Execution identity remains stable,
- Execution product-event persistence starts with v1.1.0; historical executions are not backfilled with synthetic lifecycle events.

## Compatibility

v1.1.0 preserves:

- existing v1.0 Task identity.
- Task `definitionVersion` independence from product version.
- existing Workspace / Datasource ownership boundaries.
- existing persisted Realtime CDC state identity by Workspace / Task / definitionVersion.
- manual Offline / Realtime execution.

## Known Limitations

v1.1.0 deliberately does not include:

- Distributed Runtime / Worker / HA.
- Leader election or distributed fencing.
- Exactly-once transaction coordination.
- QUEUE / PARALLEL Offline concurrency.
- Continuous Realtime recovery watchdog.
- Durable cross-process Retry timer.
- Auto Create Table.
- Logical Data Modeling.
- Multi-table Task.
- Transform.
- PostgreSQL CDC.
- Paimon / Hive / File connector expansion.
- Object-storage Runtime Trace backend, Trace retention policy, full-text Trace search or REALTIME Runtime Trace.

Additional UI boundary:

- Retry Policy does not yet have a dedicated configuration UI.

The corresponding backend contracts exist and Operations Center can observe their runtime state.

## Deployment Note

Realtime restart continuation depends on the persisted Yak Ops data directory.

Production deployments must preserve:

```text
${yak.ops.home}/data
```

Container replacement must keep the mounted data volume. Deleting that state removes the persisted Debezium offset/schema history required for continuation and the local Offline Execution diagnostic Trace history.
