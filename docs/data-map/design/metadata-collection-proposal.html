Design Proposal · 待评审

把「元数据采集」从任务列表，做成可观测的数据接入控制台

现在的采集页只回答「有哪些任务」，不回答「接到了什么、上次为什么失败、这次变了什么」。 本提案把页面重排为「健康带 + 任务表 + 任务详情抽屉 + 实例记录」四层，绝大部分由现有接口拼出； 唯一需要后端配合的是给任务列表补三个查询参数，健康带聚合与质量血缘分列后续阶段。

DECISION 01

布局：卡片列表 → 表格 + 抽屉

列表承担横向比较（范围、调度、最近实例、产出），详情抽屉承担纵向追溯（运行历史、失败表、范围）。

DECISION 02

状态：上线态与实例态分列

「已上线」不再显示为「运行中」。并新增派生态「部分成功」——采集完成但仍有失败表，此时不做缺失判定。

DECISION 03

未来能力：以示例位分阶段接入

质量、血缘不阻塞本期。页面上以「示例」标注呈现，可一键关闭，避免被误读为已交付能力。

改动范围 yak-ops-ui/apps/web/app/data-map/tasks/**
现有接口 GET /tasks · GET /crawls · GET /crawls/{id} · POST run · POST retry
后端改动 P0 无 · P0.5 三个查询参数
依赖提案 FYOIP-16 / FYOIP-17（仅占位）
01

业务现状：一个任务 = 一个命名空间的一次枚举

先对齐事实。下面六条决定了页面能展示什么、不能展示什么，后续所有设计都在这个边界内。

STEP 1数据源MySQL / PostgreSQL / Oracle / ClickHouse，凭据由数据源模块托管
›
STEP 2采集任务数据源 + 库（+ schema）、调度、排除规则、负责人
›
STEP 3采集实例PENDING → RUNNING → SUCCEEDED / FAILED，后台 worker 执行
›
STEP 4资产目录表与字段写入数据地图，记录新增 / 更新 / 缺失 / 失败
›
STEP 5下游消费资产详情、搜索、我的数据、后续的治理与血缘
失败分支：实例 → 逐表失败清单（最多 200 条）→ 仅重试失败表；命名空间 ≥2000 表在读取任何列之前即拒绝，单次执行另有 30 分钟预算。

触发只有两种

手动执行，或 Quartz Cron 周期调度。没有依赖触发、没有事件触发，也没有跨任务编排。

并发由唯一索引兜底

同一数据源同时只允许一个 PENDING / RUNNING 实例，冲突返回 CRAWL_BUSY。一个数据源可以挂多个任务，只要不同时跑。

「成功」不等于「干净」

SUCCEEDED 表示枚举完成，但可能有失败表；只有零失败的那次才判定缺失（MISSING）。

排除规则是「不采也不判缺失」

正则或精确表名命中的表保持存活但跳过采集，因此它们既不会刷新，也不会被标记缺失。

元数据是当前态，不是快照

资产保留同一身份跨多次采集，人工维护的描述、负责人、数据域、标签不会被采集覆盖。

没有的：质量与血缘

治理规则扫描（FYOIP-16）与资产关系注册（FYOIP-17）都尚未实现，页面不能凭空造数据。

01

状态语义混叠ticket 05

任务状态 RUNNING 渲染成「运行中」，与实例状态「采集中」同屏并存。用户无法判断是「配置生效了」还是「正在跑」。

02

运行不可追溯

列表只有一行 lastRun 摘要。接口其实已具备 GET /crawls?taskId=、GET /crawls/{id}（含逐表失败）与重试端点，但 UI 没有任何入口，/crawls 路由直接重定向回任务页。

03

「部分成功」被涂成绿色

实例 SUCCEEDED 且 failedCount > 0 时，界面只显示「已完成」。这正是不做缺失判定的那一类，语义上最需要提醒，却最容易被当成健康。

04

范围与产出不可见

采集范围只在编辑页可见；实例的 added / updated / removed / failed / filtered 五个计数从不展示。采完之后「发生了什么」没有落点。

05

操作不可读ticket 04

四个纯图标按钮，hover 才浮现；最常用的「立即采集」是播放图标，紧邻电源图标，误触成本高。

06

无搜索、无筛选、无批量采集

任务多时只能翻页；批量操作只支持「下线 / 删除」，最需要批量化的「立即采集」缺席。

07

只有任务视角，没有数据源视角

用户的心智是「这个库接进来了吗」。未接入的数据源在采集页完全不可见，也无从判断覆盖率。

03

三个方向，选 B

约束是：本期不动后端契约、不改任务模型。在这个前提下比较三种信息组织方式。

方案 形态 优势 代价 / 风险 结论
A · 增强现有卡片 保留卡片列表，补齐范围、产出、失败数与文字操作 改动最小，一天可上 卡片天然不适合横向比较；任务变多后仍需逐张阅读，且放不下运行历史 不选
B · 采集控制台推荐 健康带 + 任务表（可搜可筛）+ 行内详情抽屉 + 全局实例记录 横向比较与纵向追溯各归其位；抽屉复用列表上下文，不丢筛选；主体能力可由现有接口拼出 需要新增抽屉与实例记录两套视图；健康带部分指标需聚合接口（P1） 采用
C · 以数据源为中心 首屏是数据源卡片，展开后看库 / schema / 任务 最贴合「库有没有接进来」的心智，覆盖率天然可算 与「一个任务 = 一个命名空间」的模型冲突；一个数据源可挂多任务，需要重构导航与权限；改动越界到数据源模块 列为演进

选 B 的核心理由是抽屉：它让「列表负责扫视、详情负责排查」成立，且关闭后回到原筛选位置。C 的信息价值更高，但需要先回答「一个数据源多个任务如何合并展示」，不适合与本期同时做——本提案把 C 作为 P2 的演进方向记录在案。

已上线任务需先下线才能删除

按区域说明（原型内未标注编号，避免遮挡内容）：

1
页头副行：改成「看三件事」，一句话说明这页的用途；功能描述下放到文档，不再占用首屏。
2
健康带：四张等高卡，右上角标时间窗（当前 / 近 24h），避免「7 天」与「24 小时」混用；只有失败表卡是强调态且可点筛选。

状态矩阵与边界规则

两套状态必须正交表达。下表是渲染规则，「部分成功」由前端派生，不新增后端枚举。

上线最近实例列表呈现允许的操作判缺失
草稿尚未运行草稿 未运行 副行「上线后才会按调度执行」编辑 / 上线 / 删除否
已上线未运行已上线 未运行采集 / 编辑 / 下线否
已上线排队中 / 采集中采集中 副行「已运行 42 秒」，5 秒轮询编辑禁用 · 下线禁用 · 删除禁用否（未结束）
已上线成功（0 失败）成功 副行「3 小时前 · 1分20秒」采集 / 编辑 / 下线是
已上线部分成功（failedCount > 0）部分成功 副行「12 张表失败」采集 / 仅重试失败表 / 编辑 / 下线否
已上线实例级失败失败 副行给原因摘要，左侧红条重新采集 / 编辑 / 下线否
已上线重试实例部分成功 副行标注「重试」同对应终态否（重试恒不判）
已下线任意终态已下线 保留最近结果，调度列显示「已停止」上线 / 编辑 / 删除；采集禁用否

两处容易写错的操作约束：实例级失败不能「重试」——重试接口要求源实例存在失败表，没有失败表时直接被拒，只能重新发起一次采集；已上线任务不能直接删除——只能下线后再删。矩阵里的「允许的操作」按这两条收紧。

必须处理的边界

并发：同数据源只允许一个活跃实例

点击「采集」前先判断该数据源是否有排队中/采集中实例。有则置灰并提示「数据源正在采集（任务：订单库 · 全库采集）」，而不是等接口返回「该数据源已有进行中的采集任务，或采集队列已满」再报错。

规模：≥2000 表直接拒绝

拒绝发生在读取任何列之前，因此很快。前端要给出可执行的原因（缩小 schema 或加排除规则），不能只显示「采集失败」。排除表本身另有 500 张上限。

时长：30 分钟预算

预算按墙钟时间在两次元数据调用之间检查，超时即以失败结束。运行中的实例显示已运行时长；超过约 25 分钟时在抽屉内提示「接近单次预算，可能被中断」。

失败表上限 200 条

详情接口只返回前 200 条失败表并标注「仅显示前 200 张」。重试作用于该实例的全部失败表，不支持单表勾选重试。

三种空态要分开

①没有任务 → 引导新建并说明「一个任务对应一个库」；②有任务但从未运行 → 行内「未运行」，不弹空页；③筛选无结果 → 保留筛选条并提供「清除筛选」。三种都在原位置解决，不跳页。

权限与删除

本版本所有空间成员可浏览、采集、编辑。删除任务只删配置、保留已采集资产；删除数据源会级联删资产——两处文案必须说清差别，且删除入口不在主操作旁边。

新建 / 编辑页只改三处

范围预览提前

10

待确认

以下五点会改变设计，需要评审时给出结论；未定之前按括号内的默认假设推进。

覆盖率的口径是「已采集表 / 数据源内全部表」，还是「已接入库数 / 可接入库数」？前者需要逐库枚举表数，成本高且会与采集并发冲突。（默认：P0 不做覆盖率，只展示绝对量）
任务的负责人是否等同于资产责任人？当前 ownerId 只挂在任务上，若治理 Issue 要指派给责任人，两者需要打通还是各自独立？（默认：独立，抽屉内只做展示）
是否允许一个数据源挂多个任务覆盖不同 schema？若允许，批量采集必须按数据源串行；若不允许，应在创建时校验。（默认：允许，串行提交）
实例保留多久？目前没有任何清理任务，实例与失败表是永久保留的；一旦要加保留策略，列表必须显式标注时间范围，否则用户会把「历史变短」当成 bug。（默认：按现状不标注，只在页签写「近 7 天」）
「立即采集」是否对已下线任务开放？现版要求先上线才能运行。建议允许下线任务手动跑一次，语义更接近「调试」。（默认：保持现版约束，按钮置灰并说明）
v0.2

本轮 review 改了什么

上一版的问题集中在「信息都画上去了，但主次没排开」。下面八条是本次主要调整，都可在原型里直接看到。

01 · 首屏减负

KPI 由五张等宽卡收为四张，示例健康分降为页签旁一枚 chip。首屏只剩真实指标，且只有失败表卡是可点的强调态。

02 · 一列一个重点

上线态从彩色徽章改为圆点 + 文字，运行态独占徽章。原先两枚徽章并排，扫视时无法区分「配置生效」与「正在跑」。

03 · 列表减列

「近 7 天产出」四元组下移到抽屉，列表只留一个「新增」。六列决策信息 + 操作，横向比较不再被数字串打断。

04 · 抽屉结论前置

概览第一块改为「本次采集」：状态、耗时、四个计数、失败表入口。配置与排除规则后移，趋势垫底。

05 · 命名去歧义

全局叫「实例记录」，抽屉内叫「运行历史」。原先两处都叫「运行记录」，范围不同却同名。

06 · 破坏性操作下沉

行内只留「采集」与「⋯」；删除再降级到抽屉的溢出菜单，并对已上线任务禁用且给出原因。

07 · 不留空壳页签

关闭占位能力时，「质量与血缘」页签整块收起，chip 同时消失；停在该页签时自动退回概览。

08 · 操作与状态对齐

矩阵补上「判缺失」列与重试实例一行；实例级失败只能重新采集（无失败表可重试），已上线任务不可直接删除。
