## Motivation

Two accepted chains produce physical tables and neither one tells the other where the result went.

FYOIP-15 made physical metadata durable: a crawl enumerates one namespace and every observed table becomes an asset in `yak_ops_data_map_table` that carries a description, an owner, a domain, tags, favourites and a change history. The catalog serves whatever the engine reports. FYOIP-11 made a logical model real: publishing generates DDL, executes it against an explicit target, verifies an existing table instead of altering it, and collects one metadata snapshot of the published table into `yak_ops_modeling_metadata_*`.

Five current facts say where they fail to meet.

- **A published table is invisible.** `ModelPublicationServiceImpl` writes the publication row, executes the DDL and collects its snapshot; nothing in that path touches 数据地图. A table the platform just created under an accepted contract appears in 资产目录 only after somebody notices the gap, creates a collection task for that namespace and runs it.
- **Nothing checks the target against the monitored scope.** `publish()` and `preview()` resolve the datasource, database and schema from the request and never ask whether a collection task covers them, so the user gets no signal at the moment the decision is made.
- **Once crawled, a model's table is ordinary.** `DataMapCrawlWorker.execute` tests each observed name against `exclude_pattern` and `exclude_tables` — both shipped in V8/V9 — and for a match calls `keepAlive`, which refreshes the sighting and deliberately skips reading columns. An operator who excludes `dwd_*` therefore stops the platform from ever noticing that 数据建模 changed a `dwd_order` column, while the model still believes its published structure is what the catalog shows.
- **One physical table can have two identities.** A published model's table exists in `yak_ops_modeling_model_publication` plus its snapshot rows, and separately as a catalog asset keyed by the four-part identity. FYOIP-15's header keeps those separate on purpose — the snapshot is a child of one publication, the asset is a child of one physical table — and FYOIP-15 Rejected Alternative 1 refused to let the snapshot become the catalog. The refusal still stands; what is missing is a link.
- **There is no origin concept.** `yak_ops_data_map_table` (V7) has no `origin`, no reference to the model that produced the table and no state for what happens when that model goes away. FYOIP-11 makes a publication immutable and a model deletion never touches the physical table, so the catalog row keeps describing a table whose owner may no longer exist and nobody is told.

This proposal closes that loop: 建模发布 → 目录可见 → 可被治理, with no crawl in between and no manual publish. It deliberately contains **no review or approval functionality**. The reason is the order of the two problems: a publication gate makes humans the workaround for a registration path that does not exist, and it would put platform-generated, already-governed tables in the same queue as an unknown staging database's `tmp_*` residue. Close the loop first; gate it in a separate proposal once there is something real to gate.

## Public Interfaces

### Product behavior

| Item | Contract |
| --- | --- |
| Registration | A publication that reaches `SUCCEEDED` registers its table in 数据地图: one asset under the physical identity key, `status = ACTIVE`, `origin = MODEL`, `origin_ref = modelId`, `origin_state = ACTIVE`, observed columns refreshed from the model's field contract, and `published_by`/`published_time` stamped with the publisher. The user does not crawl and does not publish again. |
| Registration path | Two attempts, one guarantee. The publish request attempts registration **synchronously at the HTTP boundary, with a 2-second budget**, so a normal publish returns with the asset already in 资产目录 and the state reading `SYNCED`. Behind it the publication row is the durable queue: its terminal status and `catalog_sync_status = 'QUEUED'` are written by the same statement, and a data-map sweep keeps draining anything the fast path did not finish — timed out, threw, or lost to a process crash. A publish response therefore never waits on 数据地图 beyond the budget, and a slow or broken catalog can never fail a publication or be the reason a user cannot find their table. |
| Idempotence | Publishing the same model twice refreshes one asset and never duplicates it; replaying a registration after a crash is safe because the asset is addressed by the physical identity key. |
| One model per table | One physical table admits one active model. A second model targeting it is refused until an explicit takeover, which keeps the asset's description, owner, domain, tags and favourites. |
| Model-owned protection | An exclusion rule never skips a model-published asset: its columns are read and its change history is written like any observed table's. Saving a task whose `exclude_pattern` or `exclude_tables` matches a model-published asset in that namespace is refused with the offending names **and a narrower pattern that would work**, so an operator never writes a rule that silently does nothing. There is deliberately no override checkbox: a rule that both applies and does not apply to one table has to be reconciled on every code path forever, and the fix belongs in the pattern. Each run reports how many tables it protected. |
| Scope governance | The unit of governance is `datasource + database + schema`. Before publishing, the UI asks 数据地图 whether that namespace is governed; not governed is a warning with an explicit confirmation, **never a refusal** — 数据建模 and 数据地图 are separate domains, the published table is already a physical fact, and a consumer cannot be allowed to hold the producer's critical path. A confirmed publication causes exactly one `OFFLINE` collection task for that namespace, with no exclusion rules and the publisher as owner: creating the task saves the operator from typing the datasource and namespace by hand, while whether and when to put enumeration load on a live database stays a human decision, because the publisher cannot know what that database is doing right now. Registration never depends on the task. |
| Model removal | Deleting or offlining a model never deletes the asset. Its `origin_state` becomes `ORPHANED`, it stays visible and searchable, and the catalog surfaces it for a human decision. This is the same rule V7 already states for assets in general: an asset survives the deletion of whatever created it. |
| Failure of registration | A physical publication stays `SUCCEEDED` when catalog registration fails. The state is recorded on the publication row as `QUEUED`/`SYNCING`/`SYNCED`/`FAILED` with bounded text and an attempt count; below the ceiling the sweep retries, and past it the row stays `FAILED` and visible on screen rather than disappearing, until a manual endpoint re-runs the same code path synchronously. A `SYNCING` row becomes claimable again once it is older than the sweep's age threshold, so a claimant that died or was abandoned mid-attempt cannot strand a table. |
| Curation attribution | Every accepted curation write stamps the asset row's existing `update_by`/`update_time`, and the detail page shows who last wrote the description, owner or domain. |
| Visibility | 资产目录 gains an `origin` facet and badges so a model-published table is distinguishable from a crawled one, and an orphaned one from a live one. |
| Access | Unchanged from FYOIP-15: every Workspace member browses, crawls, curates and tags. This proposal adds no role, no gate and no permission tightening. |
| Operator logs | Collection instance logs and dashboards stay in 运维中心. This module links to them and adds no terminal panel and no log store. |

### Persisted formats

`V10` is additive. Against `yak_ops_data_map_table`: `origin` (`CRAWL`/`MODEL`, default `CRAWL`), `origin_ref`, `origin_state` (`ACTIVE`/`ORPHANED`, default `ACTIVE`), `published_by`, `published_time`, and one index on `(workspace_id, origin, origin_state)`. Against `yak_ops_data_map_crawl`: nullable `protected_count`. Against `yak_ops_modeling_model_publication`: `catalog_sync_status` (`QUEUED`/`SYNCING`/`SYNCED`/`FAILED`, nullable for rows that predate V10) with a `CHECK` over those four values, matching the constraint V4 already puts on that table's `status`, plus `catalog_sync_error`, `catalog_synced_time`, `catalog_sync_attempts NOT NULL DEFAULT 0`, `catalog_scope_confirmed NOT NULL DEFAULT 0` and one index on `(status, catalog_sync_status)` for the sweep's selection. The initial value is named `QUEUED` and not `PENDING` because that table's own `status` column already means `PENDING` for "the DDL has not run yet"; the two enums live in different columns, and the sweep's predicate is `status = 'SUCCEEDED' AND catalog_sync_status = 'QUEUED'`, so the prose and the SQL must never have to disambiguate them.

No table is created. The asset identity key, the namespace columns, the existing `crawl` counters and every cascade from V7 through V9 stay byte-identical; applied migrations are never edited.

## Proposed Changes

### 1. One asset per physical table, written by 数据地图

Data-map remains the only writer of catalog rows. Registration resolves the asset through the same identity lookup `DataMapCrawlWorker.persist` already uses (`findByIdentity`, with `adoptLegacyScope` for pre-scoping rows), then writes the observation the publication just produced: table type and remarks from the model, the columns of the published contract, `origin`/`origin_ref`/`origin_state`, and the publisher as `published_by`. It is one transaction per table, the shape `persist` already commits to through the injected `TransactionTemplate`.

The identity is built with V7's own convention: the publication's `physical_database`/`physical_schema` map onto the asset's `database_name`/`schema_name`, and a null schema becomes the empty string, so a model published into an engine that has no schemas resolves to exactly the row a crawl would produce for that table rather than to a second asset with a different key.

The payload is re-derived from durable state — the model's field contract and the snapshot `MetadataCollector` already stores — rather than carried in a message, because both are already readable from data-map through the existing `yak-ops-business-datamap` → `yak-ops-business-modeling` direction. No table stores a copy of what two modules can already read.

One ordering this exposes: V4 nulls `model_id` when a model is deleted and never deletes the publication, and the snapshot hangs off the publication rather than the model. A publication whose model is gone before the queue drains therefore re-derives from the stored snapshot alone and registers directly as `ORPHANED` — the table is a physical fact and its structure is still known; only its owner is not.

`origin` is written only by registration and by the identity default; the crawler never overwrites it. That asymmetry is what makes the protection in §3 possible, and it is why the column has a real writer today instead of being a placeholder for tomorrow's gate.

### 2. The publication row is the queue

`publications.finish(...)` and `publications.reconcile(...)` are each one UPDATE today, and each becomes one UPDATE that writes the terminal status *and* `catalog_sync_status = 'QUEUED'` in the same SET list. That single-statement atomicity is the entire durability argument: there is no window in which the platform knows the table exists physically but holds no record that the catalog still owes it an asset. `publish()` cannot be one transaction and is not asked to be — the row is inserted as `PENDING`, the DDL executes against an external datasource outside any transaction, and the terminal state lands in the later `finish` — so the terminal write is the only commit point that matters, and it carries the registration debt with it.

The repository has no event infrastructure: no `ApplicationEventPublisher`, no `@EventListener` and no `TransactionalEventListener` appears in any module. A Spring listener would be a same-process call whose delivery dies with the process in the gap between commit and handling, which is exactly the window this design refuses to lose a table through. There is therefore no event to lose and nothing to reconcile against a dropped message.

Data-map drains the queue on the `@Scheduled` seam `DataMapCrawlTaskScheduler` already uses, selecting `SUCCEEDED` publications that are owed a registration through one read method on `ModelPublicationService` — the same compare-and-set discipline `advanceNextFire` applies to crawl scheduling, applied to a row instead of a timer. Every attempt — the inline one below and the swept one — starts by claiming the row: one conditional UPDATE from `QUEUED` to `SYNCING` that also increments `catalog_sync_attempts` and returns zero rows when someone else already holds it, so exactly one caller ever runs the body per claim. A `SYNCING` row older than an explicit age threshold (at least one sweep interval) is claimable again, so a claimant that died mid-attempt cannot strand a table. Completion is written the same way: the UPDATE that moves the row to `SYNCED`, back to `QUEUED`, or to `FAILED` is guarded by the attempt count the claimant incremented, so an attempt the request gave up on can never overwrite the state of an attempt that legitimately took its place. Below the ceiling a failure returns the row to `QUEUED` with its bounded error for the next sweep to retry; at the ceiling it becomes `FAILED` and stays there with its error on screen, and only the manual retry endpoint claims a `FAILED` row, resetting the count. `catalog_synced_time` stamps success. The body is idempotent because the asset is addressed by the physical identity key, so a re-claim after a partial crash is safe rather than merely likely.

**The fast path.** Periodic convergence alone is a bad experience: a publisher who sees 发布成功 and then finds nothing in 资产目录 concludes the platform is broken. So the HTTP boundary tries registration inline — `DimensionModelingController` publishes, and when the returned record reads `SUCCEEDED` it calls data-map's registration service on a **2-second budget** before answering. Nothing illegal happens in the dependency graph: boot already depends on both modules and only ever points at them, modeling still knows nothing about data-map, and the business-to-business direction stays `yak-ops-business-datamap` → `yak-ops-business-modeling`. The budget is the hard part and it is explicit: the call runs on a bounded executor and the request gives up waiting after two seconds rather than letting a stalled catalog read, a slow datasource or a lock hold up a publication that has already physically succeeded. Giving up on the wait changes nothing about correctness: the abandoned body keeps running on its own thread and its completion UPDATE is guarded by the attempt count it claimed, so it stamps `SYNCED` only while the row still carries that count, and otherwise writes nothing and leaves the `SYNCING` row for the sweep to re-claim once it ages and repeat an idempotent registration. The publish response reports whichever `catalogSyncStatus` the request actually observed, so the UI says 已登记 or 登记中 from a fact rather than a guess.

The crash windows are then all covered by the same mechanism: killed after `finish(SUCCEEDED)` and before any attempt → the row reads `QUEUED` and the next sweep registers it, which is the same residue class `reconcile` already settles for status itself; killed mid-attempt → the row reads `SYNCING` and becomes claimable once it ages; failure inside registration → the data-map transaction rolls back, the attempt count rises and the replay is idempotent; a ceiling breach → the row stays `FAILED` with its error on screen. Rows predating V10 keep `NULL` sync state and are never replayed, so an upgrade does not retroactively register last year's publications. Normal latency is the inline attempt; worst-case latency is one sweep interval (30 seconds by default), which only the failure path ever sees.

### 3. Model-owned tables leave the exclusion path

Exclusion is decided in `execute` by testing an observed name against the run's snapshot of `exclude_pattern` and `exclude_tables`. A model-published asset must not be testable away, so the run loads one set before the loop — `listModelOwnedNames(workspaceId, datasourceId, databaseName, schemaName)`, index-backed by the identity key — and a name in that set skips the exclusion branch entirely: its columns are read, `persist` runs, `DataMapChangeDetector` records what changed. The count of such tables lands in `protected_count`.

Two consequences are worth stating plainly. First, an out-of-band `ALTER TABLE` on a model's table now reaches the change history instead of being silently excluded, which is the drift signal the catalog was missing. Second, the protection has a real limit: data-map can keep observing a table 数据建模 owns, but it has no authority to redefine its structure — the fix for drift is a model change, and that conversation belongs to the gate proposal, not here.

The save-time refusal and the runtime protection are two different jobs, and neither is optional. The refusal is what keeps the configuration honest: an operator who types `^dwd_` while `dwd_order` belongs to a model is told so immediately, with the table names and one narrowed pattern that preserves the intent (`^dwd_tmp_`), instead of discovering weeks later that a rule silently failed to cover a table. The runtime check is what covers the case no save can see — a model published later into a namespace whose rule predates it — and the run reports it as `protected_count` rather than leaving the operator to puzzle out why a listed table still appears.

An override flag is deliberately absent. A rule that both applies and does not apply to the same table has to be reconciled in the enumeration loop, in `markMissing`, in the counters and in every future read of exclusion, and each of those is a branch somebody has to remember. Narrowing a pattern is a one-line change made by the person who owns the rule; the compatibility logic would be paid for on every run forever.

`markMissing` needs no change. An excluded table is already protected from retirement by `keepAlive`, and a model-owned table that genuinely disappears from the source must become `MISSING`, because that is a true fact about a governed asset.

### 4. Scope confirmation is asked from the UI and settled by the owner of the data

The publish dialog cannot learn about collection tasks from modeling, and modeling must not read 数据地图's tables. So the check is a data-map read endpoint and the composition is the client's: the dialog asks `/crawl-tasks/scope`, shows 未纳管 as a warning with a confirmation, and sends `confirmUnmanagedCatalogScope` on the publish request. Modeling persists the confirmation on the publication row — the durable record of a decision made by a person, which the sweep needs because registration happens later — and data-map's registration step creates the one `OFFLINE` task when the confirmation is set and the namespace is still unmanaged.

Publishing without confirmation behaves identically except that no task is invented: the asset is registered, and the scope gap is reported by the same read endpoint. Registration never waits for a task, because requiring monitored scope before a publication could be visible would put 数据地图 back on the publication's critical path.

**Neither half of the confirmation is allowed to harden into a gate.** 数据建模 and 数据地图 are separate domains with separate owners: the DDL has already executed, the table is a physical fact, and a consumer that has not yet been pointed at the namespace gets no veto over work the producer has already committed — that is precisely the coupling a catalog must never earn. Symmetrically, the task the confirmation creates is `OFFLINE` by design. Sparing the operator from typing the datasource, database and schema by hand is a convenience the platform can safely provide; deciding when to start enumerating a live database is not, because the publisher cannot know what that database is carrying this hour. The platform records the gap the moment it appears, and a person decides when to open it.

### 5. One model per table, and takeover that keeps the governance

Registration refuses a second model on a table whose `origin_ref` names a different live model, with an error that names the owning model. An explicit takeover re-points `origin_ref` and changes nothing else: description, owner, domain, tags and favourites survive, because they are Workspace governance, not the old model's property. Takeover is a publication action and needs no new endpoint beyond the confirmation flag on the publish request.

### 6. Origin state is reconciled, not hooked

Model deletion has to flip `origin_state` without modeling knowing anything about data-map. The sweep that drains registrations also reconciles origin: for assets with `origin = MODEL`, it asks modeling whether `origin_ref` still resolves to a live model and writes `ORPHANED` when it does not — one conditional update, idempotent, and a re-created or re-taken-over model returns the row to `ACTIVE`. Nothing hooks into model deletion, so a deletion that happens while data-map is down cannot be missed, and no reverse dependency is introduced.

### 7. Attribution through columns that already exist

`yak_ops_data_map_table` carries `create_by`/`update_by NOT NULL` from V7, filled through `BaseEntity`, but no curation path writes the latter: `updateCurated` names only the three curated columns, and `updateObserved` and `markMissing` set `update_time` but never `update_by`, so `update_by` freezes at insert. Adding `update_by = #{actor}, update_time = #{now}` to the curation statement makes the last writer of a description or owner identifiable with no migration, and the two column sets stay unreachable from each other — the invariant `DataMapTableMapper` documents as "no merge rule needed". A crawl therefore can never erase a curator's name. What this does not buy is history: consecutive edits leave one name and there is no undo, and the sequence is the unified audit module's subject.

### 8. Explicitly out of scope

**The publication gate in every form**: `publish_status`, a staging queue, reviewed column snapshots, `review_required`, change approval, ignore and its tombstone, retention of unpublished rows, retract, batch review and the manager-only operation surface. Their design is settled on paper and is recorded as deferred; it will be proposed as its own FYOIP once this loop ships, and it will build on `origin`, `origin_ref` and `origin_state` rather than invent new identity. `publish_status` is not added here as a column that every row sets to `PUBLISHED` by default, because a constant with no writer and no reader is a placeholder, and it would make the gate look decided while forcing every existing asset through a migration it does not need.

Field, model and metric entities, relation edges and cross-type search — FYOIP-17, whose Phase 0 also owns the stable column identity change (`uk (table_id, ordinal)` → `(table_id, name)`). Lineage, quality, MDM. Scheduled crawl execution on Yak Flow. Terminal logs and run dashboards. A domain audit table, deferred to the unified audit module.

## Compatibility, Deprecation, and Migration Plan

**Relation to accepted proposals.** FYOIP-11's `Metadata` and `Deletion` rows are amended: a successful publication additionally registers a catalog asset, and a model removal leaves an `ORPHANED` asset instead of an observation nobody receives. Its create-or-verify, target-explicit and immutable-publication rules are untouched. FYOIP-15 is not amended: access, curation and the "browse everything observed" contract stay as accepted, and its Rejected Alternative 1 still holds — `yak_ops_modeling_metadata_*` gains no governance column and does not become a catalog. Its Rejected Alternative 2 is narrowed rather than reversed: what was refused was a second catalog writer with different semantics reading publication snapshots; here 数据地图 remains the only writer, the payload is one observation of one table, and the resulting asset is indistinguishable from a crawled one except in `origin`.

**Migration.** V10 is additive with safe defaults, so existing rows read `origin = CRAWL`, `origin_state = ACTIVE` and `NULL` sync columns, and no asset changes visibility, ownership or searchability during the upgrade. The dev-environment decision recorded for this proposal's earlier scope — clearing 数据地图 table, column, change, tag-link, favourite and view rows because every asset would land in a `PENDING` state and vanish from the catalog — is **withdrawn**: with no gate there is nothing to hide, and no existing asset data is deleted or backfilled. Consequently the production backfill release blocker that accompanied it no longer applies to this proposal; it returns with the gate proposal, which will need it.

Two statements change shape rather than content, and both are where the guarantees live: `finish`/`reconcile` stay one UPDATE each and gain the sync state in the same SET list (splitting them into an UPDATE plus a message write is what would create the lost-registration window), and `updateCurated` gains `update_by`/`update_time`.

**Behavior changes to expect.** 资产目录 grows: published models' tables appear without a crawl, on the normal path within the publish response itself, and stay current even when an exclusion rule matches them. `protected_count` and the `origin` facet are new output. Nothing that was visible becomes invisible, and no endpoint is removed; response payloads gain fields only. The first consumer of `GET /api/v1/data-map/tables` is the bundled UI, which gains the badges and the scope confirmation in the same release.

**Sequencing.** This proposal releases first, and FYOIP-17 may not open its Phase 0 until this one has run in production for at least two weeks with no open P0 or P1 defect attributable to the registration path; starting the registry on release day was refused by the maintainer decision of 2026-10-28. The reason is not the migration count — one forward migration is cheap — it is that a registry is the platform's identity foundation and the column-key change moves a constraint every data-map query depends on; doing both while the registration path is still finding its bugs stacks an unproven write path on top of an unstabilized schema. FYOIP-16 therefore writes its provenance and registration columns onto `yak_ops_data_map_table` and lets FYOIP-17 move them onto the envelope later, which is the accepted cost of ordering rather than a design accident. Estimated 14–20 person-days including the fast path, the sweep, scope confirmation, protection, orphan reconciliation, tests and the UI work.

Existing checks and constraints stay intact: the identity key, the `NOT NULL DEFAULT ''` namespace columns, `uk_data_map_crawl_active`, the Flyway immutability rule and the ban on `flyway repair` to mask incompatible history. Rollback is forward-only; V10 is not reverted by dropping columns.

## Test Plan

**Unit.** Identity resolution for registration, including the pre-scoping legacy row path; the model-owned name set against a pattern and against an explicit table list; scope comparison of a target against enabled task namespaces; takeover refusal and the fields it preserves; the attempt ceiling's arithmetic; `catalogScopeConfirmed` deciding task creation and nothing else.

**Database integration.**

- Publish a model → the asset exists with `origin = MODEL` and `ACTIVE`, its columns match the published contract, and no crawl ran. Publishing the same model again refreshes the same row id.
- The fast path answers inside the request: a normal publish returns with `catalogSyncStatus = SYNCED` and the asset already listable. A registration made to exceed the 2-second budget returns the publish response on time with the publication still `SUCCEEDED` and the row at `SYNCING`; the abandoned attempt converges to `SYNCED` either by finishing on its own or by the sweep re-claiming the aged row. An inline attempt and a sweep racing the same publication produce one registration, because the loser's claim updates zero rows. A `SYNCING` row is claimable only past the age threshold, never immediately. An abandoned claimant whose body completes after the row was re-claimed writes nothing at all, because its completion UPDATE is guarded by the attempt count it claimed.
- A process killed after `finish(SUCCEEDED)` and before any attempt is picked up by the next sweep and reaches `SYNCED`; a failure inside registration leaves the asset transaction rolled back and the row back at `QUEUED` with its error below the ceiling. A publication whose model was deleted before the queue drains registers from the stored snapshot alone and lands as `ORPHANED`. A model published into an engine with no schema resolves to the same asset row a crawl produces for that table, not to a second one.
- Registration failure keeps the publication `SUCCEEDED` and stores bounded `catalog_sync_error`; the ceiling stops the row at `FAILED` with its error and does not loop; the manual retry endpoint converges it to `SYNCED`. Pre-V10 rows with `NULL` sync state are not replayed.
- Exclusion versus models: saving a pattern or list that matches a model-published asset in the namespace is refused with the names and one narrowed pattern that would have saved; no request shape accepts an override; the preview endpoint reports the same collision without failing; a model published into an older matching rule is still observed, its columns refreshed, counted in `protected_count`, and never marked `MISSING` by that rule. Out-of-band drift on such a table reaches `yak_ops_data_map_table_change`.
- Model deletion or offline keeps the asset, flips `origin_state` to `ORPHANED` with description, owner, domain, tags and favourites intact, and a later re-registration returns it to `ACTIVE`. A second model targeting the same table is refused, and an explicit takeover re-points `origin_ref` while keeping every curated field.
- Curation stamps `update_by` to the actor and a following crawl run leaves that value and the curated columns untouched.
- Existing workspace isolation, datasource-cascade and run/task cascade behavior is re-verified unchanged: nothing in this proposal relaxes a V7 or V9 cascade.

**Playwright (browser-facing only).** Model path: publish a model → the publish result already reports 已登记 and the table is in 资产目录 with a 模型发布 badge → drill to the model → delete the model → the badge reads 来源已失效 and the asset stays searchable. Exclusion path: create a task with `^dwd_` while a model owns `dwd_order` → save refused with the table name and a suggested narrower pattern → apply the suggestion → save succeeds. Scope path: publish into an unmanaged namespace → the confirmation is shown with the reason → confirm → the 采集任务 list holds one new `OFFLINE` task owned by the publisher, still offline. Curation path: edit a description as a member → the detail page shows that member as the last writer → run a crawl → the writer is still that member.

**Performance and operations.** A 2,000-table run with the model-owned set preloaded, proving the protection adds one index-backed query rather than one lookup per table; the registration sweep's selection query proven to use the sync-state index instead of scanning publications; a 1,000-column model publish; the fast path held to its 2-second budget against a registration made deliberately slow, with the publish response time measured in that case rather than only in the happy path; the scope endpoint at the publish-dialog latency budget. Where a suite does not run, it is reported as not run.

## Rejected Alternatives

1. **Build the publication gate in this proposal.** It was the draft this proposal replaced: `publish_status`, a staging queue, a reviewed column snapshot, ignore as a tombstone, retention, retract, batch review and a manager-only operation surface. It is the right design for the second step and the wrong first step — while registration is missing, a gate makes an operator approve a thousand tables they never asked for, hides every existing asset behind a `PENDING` default, and forces the dev-environment data reset plus a production backfill the product does not need yet. It keeps its own proposal.
2. **Require a crawl and a manual publish after every model publication.** One writer, but the user still has to do three actions to see a table the platform just created, and the table may be receiving writes while it is invisible.
3. **Reuse `yak_ops_modeling_metadata_*` as the catalog, or add governance columns to it.** The snapshot is a child of one publication: publishing twice means two rows, refreshing replaces it, deleting the publication deletes it, and it holds no owner, domain, tag or favourite. FYOIP-15 Rejected Alternative 1 stays rejected.
4. **Add a separate outbox or message table, or emit an in-process event.** A message table would duplicate the four-part target, the model identity and the publisher that the publication row already stores, needs its own cascade against deletion, and can disagree with the row it mirrors. An in-JVM event has no durability at all, and the repository has no event infrastructure to build on. Writing the registration state in the same statement as the terminal status gives the same guarantee with zero new tables.
5. **Call the data-map service from `ModelPublicationServiceImpl`.** `yak-ops-business-datamap` already depends on `yak-ops-business-modeling`; a direct call inverts it into a cycle. The queue and the drain keep one direction and give compensation a place to live.
6. **Let the exclusion rules hide model-published tables, and protect only against `MISSING`.** The `keepAlive` branch already prevents retirement, so the surviving damage is invisible structure drift on a governed table — the one thing 数据建模 exists to prevent.
7. **Refuse to publish into a namespace 数据地图 does not monitor.** 数据地图 is a consumer of publications, not an admission authority, and making it one would put catalog coverage on the publication's critical path. The warning plus confirmation keeps the decision with the publisher and closes the gap with one new task.
8. **Have the modeling publish preview read collection tasks.** Same cycle as 5, one layer earlier. The scope question is answered by 数据地图's own endpoint, and the client composes the two.
9. **Hook model deletion to flip `origin_state`.** A hook that fires while data-map is down is lost, and a hook is a reverse dependency. The sweep reconciles origin from durable rows, which converges whether the deletion happened during an outage or a restart.
10. **Delete the catalog asset when the model is deleted.** V7 already says an asset outlives the task that found it, and a table dropped by a person is still a table. `ORPHANED` is the honest state and keeps the governance a Workspace paid for.
11. **Add `publish_status` now as a defaulted column to "prepare for the gate".** A column every row sets to the same value with no writer and no reader is a placeholder, not a contract, and it would make the gate's semantics look settled before its proposal is discussed.
12. **Fold the entity registry into this proposal.** Unified `asset_entity` identity, FQN, relation edges and cross-type search change how every module registers an asset and require stable column identity first. It is FYOIP-17.
13. **Build a terminal log panel or per-run log store here.** V2's redline forbids run logs in this module, and 运维中心 owns the collection instance page. This proposal adds a counter and a link.
14. **Let an operator override the exclusion collision.** An override makes one rule simultaneously active and inactive for a specific origin, and every consumer of exclusion — the enumeration loop, `markMissing`, the counters, the preview, and anything added later — has to re-implement the same precedence. The collision is rare, mechanical to resolve and visible the moment it occurs, so the cheapest correct fix is to make the pattern precise at save time and say so in the message.
15. **Register only from the periodic sweep.** Simpler to write, and it produces the worst possible first impression of this feature: 发布成功 followed by an absent table for up to one interval, which reads as a broken platform rather than a lagging one. The sweep stays as the durability guarantee; making it also the normal path spends reliability on a latency problem the inline attempt does not have.
