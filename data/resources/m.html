SeaTunnel Web 连接器适配系列，这一篇聊 MySQL CDC。

MySQL 是最常见的数据源之一。

但在真实业务里，我们很多时候不只是想同步一张表，而是希望 MySQL 里的数据一发生变化，下游系统也能尽快拿到。

所以 MySQL CDC 的适配，不只是多支持了一个连接器，而是让 SeaTunnel Web 可以更自然地处理实时增量同步场景。
MySQL CDC

Q 为什么需要 MySQL CDC？

```

传统同步任务，很多都是定时全量同步。

比如每天同步一次，或者每隔一段时间重新拉取一遍数据。

这种方式可以用，但当数据变化比较频繁时，就会有几个问题：同步不够及时、重复读取数据、任务压力变大。

MySQL CDC 更适合处理这种场景。它关注的是数据变化本身，可以捕获新增、修改、删除，然后持续同步到下游。

```

Q 核心功能有哪些？

```

这次 MySQL CDC 适配，主要围绕几个常用能力展开。

第一，支持 MySQL CDC 作为 Source。
创建任务时，可以选择 MySQL CDC 作为数据来源，用来监听 MySQL 表中的数据变化。

第二，支持页面化配置。
数据库连接、监听表、启动模式、server-id 等参数，都可以通过页面填写，减少手写配置。

第三，支持实时增量同步。
MySQL 中发生新增、修改、删除后，任务可以持续捕获变化，并同步到下游系统。

第四，支持实时 Metrics。
任务运行后，可以在 SeaTunnel Web 中看到运行状态、同步条数、QPS、耗时等指标，方便判断任务是否正常。

第五，支持任务运行日志查看。
如果任务启动失败，或者同步过程中出现异常，可以直接在页面查看日志，减少排查成本。

```

Q 可以解决什么问题？

```

第一个问题，是不用频繁全量同步。

对于变化频繁的业务表，如果每次都全量读取，数据量一大，任务压力会越来越明显。

MySQL CDC 只关注变化的数据，可以减少很多重复读取。

第二个问题，是数据同步不够及时。

订单、用户状态、业务流水这类数据，很多时候不适合等到下一次定时任务再同步。

通过 CDC，可以让下游更快拿到 MySQL 中的最新变化。

第三个问题，是 CDC 任务不好排查。

有了实时 Metrics 和运行日志之后，用户可以更直观地看到任务有没有在跑、数据有没有在同步、异常大概出在哪里。

```

MySQL CDC 的重点，不只是“能同步”。

更重要的是，让实时同步任务可以配置、可以运行、可以观察、可以排查。

Q 对用户来说，最直接的感受是什么？

```

对用户来说，最直接的感受其实很简单。

1. 不用自己手写复杂的 CDC 配置。

2. 可以在页面上创建 MySQL CDC 实时任务。

3. 可以看到任务运行状态和实时 Metrics。

4. 出问题时，可以通过日志和指标更快定位。

5. 从任务创建到运行观察，整体链路更加完整。

```
